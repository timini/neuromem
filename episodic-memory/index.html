    Episodic memory (EpisodicMemory)¶

    EpisodicMemory is the second memory model in neuromem-core (packages/neuromem-core/src/neuromem/episodic.py, ADR-005). It runs alongside the tag-graph model and is selected in the benchmark with --agent neuromem-episodic.

    The idea in one paragraph: record every conversation as one memory with its date, embed the whole memory, and cluster the memories hierarchically so the same memories can be grouped in many ways at many levels of abstraction. Each cluster (an episode) gets an LLM summary written as a dated history that leads with the current state, so a cluster about "where I keep my sneakers" reads like an episodic memory: what changed, when, and what is true now.

    Why a second model¶

    A review of the tag-graph model on LongMemEval found that most wrong answers were not retrieval failures. The relevant memory was usually in the prompt. The answer was wrong because:

    • no dates reached the system, so "how many days ago" and "what is my current X" could not be answered;
    • short, user-centric summaries dropped details the assistant had given;
    • the same memory was rendered under several tags, using about a third of the context on duplicates;
    • centroid vectors were averages of 1 to 4 word tag labels, which drift towards generic meanings.

    The episodic model removes tags entirely and makes dates first-class.

    Overview¶

    flowchart TD
    S["Session turns + date + session id"] --> E["enqueue_session(): no LLM calls"]
    E --> I[("ep_memories, status = inbox")]
    I --> D1["1. Dated summary per memory (LLM)"]
    D1 --> D2["2. Embed whole memory (chunk-mean)"]
    D2 --> D3["3. Merge near-duplicates into units"]
    D3 --> D4["4. Dendrograms over units, several linkages"]
    D4 --> D5["5. Episode per internal node, cached by member set"]
    D5 --> D6["6. Chronological episode summary (LLM) + 2 vectors"]
    D6 --> R1["Retrieval: score units and episodes against the query"]
    Q["Query + today's date"] --> R1
    R1 --> R2["Render: date, episodes, dated memories, transcripts"]

    Data model¶

    Storage is a self-contained SQLite database (:memory: by default, or a file path). Two tables:

    erDiagram
    ep_memories {
        TEXT id PK "mem_<12 hex>"
        TEXT session_id
        TEXT session_date "as given, e.g. 2023/05/20 (Sat) 02:21"
        REAL sort_key "epoch seconds; undated = 1e12 + insertion order"
        TEXT raw_content "full transcript, role: text per turn"
        TEXT summary "dated LLM summary"
        BLOB embedding "float32, L2-normalised"
        TEXT merged_into "canonical memory id if merged, else NULL"
        TEXT unit_summary "merged summary, on the canonical row only"
        TEXT unit_key "hash of the member set unit_summary was built from"
        TEXT status "inbox | consolidated"
        TEXT metadata "JSON"
    }
    ep_episodes {
        TEXT id PK "ep_<12 hex>"
        TEXT member_key UK "sha1 of sorted member memory ids"
        TEXT member_ids "JSON list of unit ids, date order"
        TEXT first_date
        TEXT last_date
        TEXT summary "TOPIC / CURRENT / HISTORY"
        BLOB summary_embedding "embedding of the summary text"
        BLOB mean_embedding "normalised mean of member embeddings"
        INTEGER active "1 if produced by the latest dream"
    }
    ep_memories ||--o{ ep_memories : "merged_into"
    ep_episodes }o--o{ ep_memories : "member_ids"

    A unit is the thing that gets clustered: a canonical memory plus any near-duplicates merged into it. Most units contain one memory.

    Ingest¶

    enqueue_session(turns, timestamp=None, session_id=None, metadata=None) joins the turns as role: text paragraphs and stores one row in the inbox. It makes no LLM or embedding call, so it is safe on a request path.

    Dates are parsed from the formats used by chat logs and LongMemEval (2023/05/20 (Sat) 02:21, ISO 8601 and a few others). The parsed time becomes sort_key. Undated memories sort after all dated ones, in insertion order.

    Dream cycle¶

    dream() runs the whole consolidation synchronously under a lock. If any step raises, the database transaction is rolled back so the next cycle starts from a clean state. A failed or empty LLM call does not abort the cycle: that one summary falls back to the raw records (or the transcript head for memory summaries) and a warning is logged.

    1. Dated memory summaries¶

    Each new memory is summarised with one LLM call (MEMORY_SUMMARY_PROMPT), in parallel across workers threads. The prompt gets the session date and must:

    • start with "On YYYY-MM-DD (Day),";
    • convert every relative time expression into an absolute date, keeping the original phrase in brackets ("on 2023-05-13 (last Saturday)");
    • keep every personal fact: possessions, purchases, places, people, amounts, counts, durations, preferences, plans and changes of mind;
    • state changed values explicitly ("The user now keeps X in Y");
    • keep the concrete specifics the assistant gave: names, numbers, list items with their numbers, steps, moves;
    • run 3 to 10 sentences depending on content.

    2. Whole-memory embeddings¶

    Each memory is embedded as:

    Date: 2023-05-20 (Sat)
Summary: <dated summary>

Transcript:
<full transcript>

    Embedding APIs silently truncate long input: both gemini-embedding-001 and gemini-embedding-2 accept a 40,000-character input without an error. So any text longer than embed_chunk_chars (24,000 characters, about 6,000 tokens) is split into chunks. Each chunk carries the same date and summary header, the chunk vectors are L2-normalised and averaged, and the average is normalised again. The default embedder is gemini-embedding-2, which takes about 8,000 tokens per input.

    gemini-embedding-2 is multimodal: given a plain list of strings it returns one embedding for the whole list. GeminiEmbeddingProvider therefore wraps each text in its own Content so it gets one vector per text from every model.

    3. Near-duplicate merging¶

    Memories whose embeddings have cosine similarity at or above merge_threshold (0.97) are merged. Pairs above the threshold are joined with union-find, so merging is transitive. The earliest memory in each group becomes the canonical id, and the others get merged_into set.

    A merged unit gets one LLM summary (MERGE_PROMPT) that keeps every fact and date, orders events by date, and states the latest value first where values changed. The summary is rebuilt whenever the unit's member set changes, which is detected by comparing unit_key with a hash of the current member ids.

    In the rendered context a merged unit appears once, with all its dates, for example [2023-01-01 (Sun), 2023-02-01 (Wed)] mem_….

    4. Many overlapping clusterings¶

    For each linkage method in linkages (default average and ward), scipy builds the full agglomerative dendrogram over the unit embeddings:

    • average, complete, single and weighted use cosine distance on L2-normalised vectors;
    • ward uses Euclidean distance on the same normalised vectors, which ranks the same as cosine distance.

    Every internal node of every dendrogram becomes a candidate episode. Identical member sets from different linkages are kept once. Sets larger than max_episode_size (30) are skipped, because a summary of 30+ sessions turns generic and the prompt gets slow.

    With N units and two linkages there are up to 2(N - 1) episodes. A memory belongs to one episode per dendrogram level above it, so it sits in many episodes at different granularities. The two linkages disagree in useful ways: average linkage tends to chain related topics together, while Ward produces compact, balanced groups.

    graph TD
    subgraph average["average linkage"]
        A1["ep: sneakers + shoe rack"] --> m1["mem 2023-01-02: sneakers under bed"]
        A1 --> m2["mem 2023-03-04: moved sneakers to rack"]
        A2["ep: home organisation"] --> A1
        A2 --> m3["mem 2023-02-10: closet clear-out"]
    end
    subgraph ward["ward linkage"]
        W1["ep: closet + sneakers"] --> w3["mem 2023-02-10"]
        W1 --> w2["mem 2023-03-04"]
        W2["ep: home organisation"] --> W1
        W2 --> w1["mem 2023-01-02"]
    end

    In this example "home organisation" has the same member set in both trees, so it is stored once; the two lower episodes differ and both are kept.

    5. Episode summaries¶

    Each new episode is summarised from its members' summaries, oldest first, each prefixed with its dates (EPISODE_PROMPT). The output format is fixed:

    TOPIC: Where the user keeps their old sneakers
CURRENT: As of 2023-03-04 the user keeps their old sneakers on the shoe rack by
the front door; before that (2023-01-02) they were in a box under the bed.
HISTORY:
- 2023-01-02: Keeps old sneakers in a box under the bed.
- 2023-02-10: Cleared out the closet, donated two pairs of boots.
- 2023-03-04: Moved the sneakers to the new shoe rack by the front door.

    The prompt also tells the model to name each distinct item when several of the same kind appear, which helps counting questions.

    Episodes are cached by member_key, a hash of the sorted member memory ids (not unit ids). A later dream cycle that produces the same set reactivates the stored episode without an LLM call. A set that changed, including a unit that gained a merged memory, gets a new summary.

    Each episode stores two vectors:

    Vector What it is Good for
    summary_embedding Embedding of the episode summary text Matching the query against the words the answering model will read
    mean_embedding Normalised mean of the member memory embeddings Pure geometry, no dependence on summary quality

    Summing member vectors instead of averaging them gives a vector with the same direction, so it ranks identically under cosine similarity and is not offered as a separate option.

    Retrieval¶

    build_context(query, today=None, ...) makes one embedding call and no LLM calls.

    sequenceDiagram
    participant A as Agent
    participant M as EpisodicMemory
    participant E as Embedder
    A->>M: build_context(question, today=question_date)
    M->>E: embed(question)
    E-->>M: q
    M->>M: score every unit: cos(q, unit vector)
    M->>M: score every active episode: cos(q, summary or mean vector)
    M->>M: take top episodes, skipping overlap > 0.8 Jaccard
    M->>M: take top units, sort chosen units by date
    M-->>A: text + memory, session and episode ids

    Scoring:

    • Units are ranked by cosine similarity between the query and the unit vector (the normalised mean of its members). The top top_memories (12) are kept.
    • Episodes are ranked by episode_embedding: "summary" (default), "mean" or "max" (the better of the two). Walking down the ranking, an episode is skipped if its member set overlaps an already chosen one by more than max_episode_overlap (0.8, Jaccard), so the context does not fill with near-identical parent and child episodes. The top top_episodes (6) are kept.

    The rendered context has four parts:

    Today's date: 2023-05-30 (Tue)

## Episodes
### Episode ep_… (3 memories: 2023-01-02 (Mon), 2023-02-10 (Fri), 2023-03-04 (Sat))
TOPIC: …
CURRENT: …
HISTORY: …

## Memories
The most relevant individual memories, oldest first.
[2023-01-02 (Mon)] mem_…: On 2023-01-02 (Mon), the user …
[2023-03-04 (Sat)] mem_…: On 2023-03-04 (Sat), the user …

## Transcripts
### mem_… (2023-03-04 (Sat))
user: …
assistant: …

    The transcripts section holds the full text of the raw_memories (3) closest units, each capped at raw_chars (12,000 characters). It is there for questions about exact details, especially what the assistant said.

    The result also lists the memory ids, session ids and episode ids used, which the benchmark uses to compute evidence recall.

    Answering¶

    The benchmark agent (NeuromemEpisodicAgent) puts the context into episodic_answer.prompt with these rules:

    • compute elapsed time from the memory dates to today's date (the question date), not the real current date;
    • the most recent dated statement of a changed fact is the current one;
    • for "how many" questions, list each distinct item with its date, remove duplicates, then count, and do not count the subject of the question;
    • quote exact details from the transcripts for questions about what the assistant said;
    • say so when the memory does not contain the answer or contradicts the question's premise.

    Cost¶

    Per dream cycle with N new memories:

    • N memory-summary calls;
    • one merge call per merged unit whose membership changed (rare);
    • one episode call per new member set, up to len(linkages) × (N − 1) on the first cycle (about 60 to 75 for a 50-session LongMemEval instance after de-duplication and the size cap);
    • one or two batched embedding calls.

    Retrieval costs one embedding call. On LongMemEval_S instances (about 50 sessions each) the first dream cycle took 400 to 600 seconds with 8 workers on gemini-3-flash-preview; the worker count was raised to 24 for the full benchmark.

    Open questions¶

    Chunks or sessions as the unit. A memory is currently a whole session. Embedding a whole session averages over everything said in it, so a brief aside (where the user keeps their sneakers, mentioned during a recipe chat) has little weight in the vector. Splitting sessions into chunks before clustering would let that aside cluster with other sneaker mentions. It would also multiply the number of units and episodes by roughly ten. A cheaper middle ground is to keep sessions as the memory but store one vector per chunk and score a memory by its best chunk. Evidence recall from the benchmark (the share of answer sessions that reached the prompt) decides whether either is needed.

    Incremental cost. Every dream cycle rebuilds the dendrograms from scratch. Episode summaries are cached by member set, but adding one memory changes the member set of every ancestor in the tree, so each new memory triggers about log N to N new episode summaries.

    Storage contract. The model uses its own SQLite tables, not the StorageAdapter contract. Adopting it as the main model would need memory embeddings and episode records in that contract.
