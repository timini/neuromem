    Tag-graph memory (NeuroMemory)¶

    This page describes the original neuromem memory model, NeuroMemory, step by step. It covers the data model, ingestion, every step of the dream cycle, retrieval, the agent tools and the tunable defaults. The pipeline, retrieval, tools and defaults sections are taken from the code in:

    • packages/neuromem-core/src/neuromem/system.py (NeuroMemory)
    • packages/neuromem-core/src/neuromem/context.py (ContextHelper)
    • packages/neuromem-core/src/neuromem/clustering.py (HDBSCANClusteringProvider)
    • packages/neuromem-core/src/neuromem/vectors.py
    • packages/neuromem-core/src/neuromem/tools.py
    • packages/neuromem-core/src/neuromem/storage/sqlite.py (SQLiteAdapter)
    • packages/neuromem-gemini/src/neuromem_gemini/llm.py and the templates in packages/neuromem-gemini/src/neuromem_gemini/prompts/
    • packages/neuromem-adk/src/neuromem_adk/enable.py and callbacks.py

    The benchmark and limitations sections draw on the documents they link to. The episodic model that runs alongside it is described in episodic-memory.md and ADR-005.

    Overview¶

    A memory is a piece of raw text, usually a whole conversation session. An LLM summarises it and extracts short tags from the summary ("degree", "Acme Corp", "task management"). Each distinct tag becomes a leaf node with an embedding of the tag text. HDBSCAN clusters the tag vectors into a hierarchy of centroid nodes, and an LLM names each centroid with one word and writes a short paragraph about what sits under it. Memories link to their tag nodes.

    At query time the query is embedded, the nearest nodes (tags or centroids) are found, the graph is walked outward from them, and the result is rendered as an indented text tree that goes into the answering model's prompt.

    The expensive work happens in a background dream cycle. Ingestion only writes a row.

    Data model¶

    SQLiteAdapter creates three tables (_SCHEMA_DDL in storage/sqlite.py). Foreign keys are switched off (PRAGMA foreign_keys=OFF), so edge endpoints are not checked by the database. The database runs in WAL mode.

    erDiagram
    MEMORIES ||--o{ EDGES : "has_tag (source)"
    NODES ||--o{ EDGES : "has_tag (target)"
    NODES ||--o{ EDGES : "child_of (source = parent)"
    NODES ||--o{ EDGES : "child_of (target = child)"

    MEMORIES {
        text id PK "mem_ plus 32 hex"
        text raw_content "NOT NULL"
        text summary "empty until dream step 2"
        text status "inbox, dreaming, consolidated, archived"
        real access_weight "default 1.0"
        integer last_accessed "NULL until retrieved"
        integer created_at "insert time, Unix seconds"
        text metadata "JSON or NULL"
        text named_entities "JSON list, default empty"
    }
    NODES {
        text id PK "node_ plus uuid4"
        text label "tag text or centroid name"
        blob embedding "float32 bytes"
        integer embedding_dim "corruption check"
        integer is_centroid "0 leaf, 1 centroid"
        text paragraph_summary "centroids only, NULL until summarised"
    }
    EDGES {
        integer id PK
        text source_id
        text target_id
        real weight
        text relationship "has_tag or child_of"
    }

    memories¶

    One row per ingested text. id is mem_ followed by 32 hex characters. created_at is the time of insertion (int(time.time())), not the date of the conversation. summary is written as an empty string at insert time and filled in by the dream cycle. named_entities is a JSON list of strings.

    status has four values, enforced by a CHECK constraint:

    Status Meaning Set by
    inbox Ingested, not yet processed insert_memory; also the rollback target
    dreaming Claimed by a running dream cycle Step 1 of the dream cycle
    consolidated Processed, linked into the graph, subject to decay Last step of the dream cycle
    archived Decayed below the threshold; tag edges removed apply_decay_and_archive

    access_weight starts at 1.0. Decay lowers it; retrieval resets it to 1.0.

    nodes¶

    One row per tag (leaf) or centroid. id is node_ followed by a hyphenated UUID4. The embedding is stored as raw float32 bytes with its dimension in embedding_dim. The first node written fixes the dimension for the whole table: upsert_node rejects any embedding of a different length, and logs a warning above 4096 dimensions. On read, a blob whose length is not embedding_dim * 4 raises StorageError.

    paragraph_summary holds the centroid's 2 to 4 sentence summary. An upsert of an existing node id sets it back to NULL.

    edges¶

    Relationship Source Target Weight
    has_tag memory id node id (normally a leaf tag) 1.0
    child_of parent centroid id child node id cluster cohesion (mean pairwise cosine of the children)

    (source_id, target_id, relationship) is unique and insert_edge uses INSERT OR IGNORE, so repeating an edge is a no-op. Indexes exist on memories(status), edges(source_id) and edges(target_id).

    Ingestion and the inbox¶

    enqueue(raw_text, metadata=None)¶

    NeuroMemory.enqueue makes no LLM call.

    1. Rejects empty raw_text with ValueError.
    2. Inserts a row with status='inbox', summary='', access_weight=1.0, last_accessed=NULL. Metadata must be JSON-serialisable.
    3. Counts inbox rows. If the count is at least dream_threshold (default 10) and is_dreaming is false, it starts a daemon thread named neuromem-dream that runs _run_dream_cycle.
    4. Returns the memory id.

    enqueue_session(turns, metadata=None)¶

    Takes a list of dicts with role and text keys (other keys are ignored). It validates the list, builds one transcript with "{role}: {text}" per turn joined by blank lines, and calls enqueue once. A session becomes a single memory. There is no timestamp parameter, so the session date is not stored.

    force_dream(block=True)¶

    • block=True: if a background dream thread is alive, join it, then run _run_dream_cycle on the caller's thread.
    • block=False: if a background thread is alive, return. Otherwise start a new daemon thread.

    Only one cycle can run at a time. _run_dream_cycle takes _dream_lock without blocking and returns at once if another cycle holds it.

    The dream cycle¶

    NeuroMemory._run_dream_cycle runs these steps in this order.

    flowchart TD
    A["Acquire _dream_lock (non-blocking)"] -->|held| Z0["Return, no-op"]
    A -->|acquired| B["Step 1: Read all inbox memories"]
    B -->|none| Z1["Release lock, return"]
    B --> C["Flip batch to dreaming"]
    C --> D["Step 2: Summary backfill (generate_summary_batch)"]
    D --> E["Step 3: Tag extraction (extract_tags_batch)"]
    E --> F["Step 4: NER (extract_named_entities_batch), write named_entities"]
    F --> G["Step 5: Tag nodes: embed new labels, upsert leaves"]
    G --> H["Step 6: HDBSCAN recursive clustering, write centroids and child_of edges"]
    H --> I["Step 7: Wire has_tag edges"]
    I --> J["Step 8: Name placeholder centroids"]
    J --> K["Step 9: Junction summaries, floor-up"]
    K --> L["Step 10: Decay and archive consolidated memories"]
    L --> M["Step 11: Flip batch to consolidated"]
    M --> Z2["Release lock"]
    D -. exception .-> R["Flip batch back to inbox, re-raise"]
    E -. exception .-> R
    F -. exception .-> R
    G -. exception .-> R
    H -. exception .-> R
    I -. exception .-> R
    L -. exception .-> R
    R --> Z2

    Steps 8 and 9 catch and log their own exceptions, so a naming or summary failure does not roll the cycle back.

    Step 1: claim the batch¶

    storage.get_memories_by_status("inbox") returns every inbox row ordered by created_at, then id. If there are none the cycle returns. Otherwise one UPDATE ... WHERE id IN (...) sets them all to dreaming. Memories enqueued after this point stay in the inbox for the next cycle.

    Step 2: summary backfill¶

    _backfill_summaries selects memories whose summary is empty or whitespace (rows that already have a summary are skipped). It calls llm.generate_summary_batch on their raw_content. If the number of summaries returned differs from the number of inputs it raises ValueError, which triggers the rollback. Results are written with set_summaries and copied onto the in-memory dicts used by later steps.

    Gemini (GeminiLLMProvider.generate_summary_batch):

    • One text goes to generate_summary (prompt generate_summary.prompt).
    • Up to 6 texts go in one call; more are split into chunks of 6 (_MEMORY_SUMMARY_BATCH_CHUNK_SIZE) and run on a thread pool of up to 10 workers (_BATCH_WORKERS).
    • Each chunk uses generate_summary_batch.prompt, which numbers the texts [1], [2] and asks for a JSON array of strings. Raw text has \n# replaced by \n first, so it cannot inject Markdown headings into the prompt.
    • If the response is not valid JSON or has the wrong length, every item in the chunk is summarised with a single call. An empty or non-string item is redone with a single call.

    The prompts ask for 2 to 4 sentences that keep personal facts about the user, proper nouns, numbers and dates, and implied facts, and that prefer personal facts over generic advice.

    Step 3: tag extraction¶

    llm.extract_tags_batch(summaries) returns one list of tag strings per memory.

    Gemini (extract_tags_batch):

    • One summary goes to extract_tags (comma-separated output, extract_tags.prompt).
    • Two or more go in one call with no chunking (extract_tags_batch.prompt), asking for a JSON array of arrays with 5 to 12 tags of 1 to 4 words each.
    • Parse failure or a length mismatch falls back to one extract_tags call per summary. A non-list inner element falls back for that item.
    • Each tag is stripped of whitespace and surrounding quotes. Lists are cut to 12 tags.

    Tags keep the casing the model returns. They are matched to existing nodes by exact string, so "Degree" and "degree" are different tags.

    Step 4: named-entity extraction¶

    llm.extract_named_entities_batch(summaries) returns proper nouns per memory (brands, products, places, people, organisations). set_named_entities writes them to the named_entities column straight away, before the remaining steps.

    Gemini uses the same shape as tag extraction: a single unchunked call with extract_named_entities_batch.prompt, per-item fallback to extract_named_entities, and a cap of 8 entities. The single-item prompt returns NONE for no entities, which becomes an empty list.

    Entities are not used for clustering or retrieval. They appear only on the annotation line of the rendered tree and in retrieve_memories results.

    Step 5: tag node creation and embedding¶

    _ensure_tag_nodes:

    1. Collects the union of tag strings across the batch.
    2. Loads every node in storage with get_all_nodes (leaves and centroids, ordered by id) into a dict keyed by label. When two nodes share a label, the one with the later id wins.
    3. Finds the labels not already in that dict, sorts them, and embeds them in one embedder.get_embeddings call. The Gemini embedder (default model gemini-embedding-001) sends at most 100 texts per request.
    4. Upserts each as a leaf (is_centroid=False) with id node_<uuid4>.

    It returns the label dict, which now holds every node in storage plus the new leaves. A tag that matches an existing label, including a centroid's label, reuses that node.

    Step 6: HDBSCAN recursive clustering¶

    _run_clustering passes every node in the label dict, as (id, embedding) pairs, to self.clusterer.cluster. That includes centroids from earlier cycles, not only the new leaves. With fewer than 2 nodes it does nothing.

    HDBSCANClusteringProvider._cluster_level then runs, starting at depth 0:

    1. Stop if depth is 8 or more (_MAX_RECURSION_DEPTH) or there are fewer than min_cluster_size (2) inputs.
    2. L2-normalise each embedding, so Euclidean distance orders points the same way as cosine distance.
    3. Run hdbscan.HDBSCAN(min_cluster_size=2, metric="euclidean", allow_single_cluster=True).fit_predict.
    4. Drop points labelled -1 (noise). Noise points get no parent at this level and are not passed up.
    5. For each cluster, emit a Cluster with:
    6. id c_ plus 16 hex characters,
    7. embedding = mean of the members' original (not normalised) embeddings,
    8. child_ids = the member ids,
    9. cohesion = mean cosine similarity over all member pairs.
    10. If this level produced at least 2 clusters, recurse on the cluster centroids at depth + 1.

    Clusters are emitted children first, so a single forward pass can write them. For each cluster _run_clustering:

    1. Creates a centroid node node_<uuid4> with is_centroid=True, the cluster embedding, and a placeholder label cluster_ followed by characters 5 to 16 of the node id (the first 12 characters of the UUID, which always include the hyphen at position 8).
    2. Writes a child_of edge from the centroid to each child, with weight equal to the cohesion. Child ids that start with c_ are mapped to the storage id created earlier; if one has not been seen yet, it raises ValueError (a provider ordering bug).

    Old centroids and their edges are never deleted, and an existing centroid never gains new child_of edges. Because every node, including leaves and older centroids, is clustered again each cycle, each cycle writes a new set of centroids over the whole graph, and a node can collect several parents across cycles.

    cluster_threshold (default 0.65) is validated and stored on NeuroMemory but the HDBSCAN provider does not read it. random_state (default 42) is stored by the provider but not passed to HDBSCAN.

    Step 7: has_tag wiring¶

    For each memory and each of its tag strings, insert_edge(memory_id, node_id, 1.0, "has_tag"), where node_id comes from the label dict. Memories link to the node whose label matches the tag exactly. No step links a memory to a centroid ancestor. A memory is linked to a centroid only when one of its tags equals that centroid's label (see step 5).

    Step 8: centroid naming¶

    _run_all_centroid_naming loads all nodes, keeps centroids whose label starts with cluster_, and calls resolve_centroid_names(placeholders, expected_placeholders=True, all_nodes=...).

    For each placeholder centroid:

    1. Children: get_subgraph([centroid_id], depth=1) and keep the targets of child_of edges whose source is the centroid. A centroid with no children is skipped.
    2. Input: the labels of the first 20 children.
    3. avoid_names: the labels of every centroid not in the set being named, skipping empty labels and labels that still start with cluster_.
    4. Batched call: llm.generate_category_names_batch(groups, avoid_names=...). If it raises or returns the wrong number of names, the whole batch goes to the fallback.
    5. First word: each returned name is cut to its first whitespace-separated word. An empty name sends that centroid to the fallback.
    6. Nearest-child fallback: _nearest_child_label returns the label of the child whose embedding has the highest cosine similarity to the centroid embedding. If the centroid has no embedding or a zero vector, it returns the first child's label.
    7. Persist: update_node_labels writes all new labels in one transaction.

    Gemini (generate_category_names_batch):

    • Groups go in chunks of 30 (_BATCH_CHUNK_SIZE) on up to 10 workers. One group uses the single-call prompt.
    • generate_category_names_batch.prompt asks for one lowercase English noun per group, bans generic nouns ("thing", "aspect", "topic" and others), asks for distinct names within the batch, and includes the avoid line.
    • render_avoid_section sorts the avoid labels alphabetically, keeps the first 30 (_AVOID_NAMES_MAX), and renders Avoid reusing these already-taken labels: a, b, c.
    • Each name is cleaned to its first token, stripped of punctuation and lowercased. A non-string item, a name in _GENERIC_LABEL_BLOCKLIST or an empty name is redone with the single-call prompt. A chunk whose response is not valid JSON or has the wrong length is redone one group at a time with the single-call prompt. If the single-call prompt also returns an empty or blocked name, the result is the first word of the first concept, lowercased, or concept if there are none.
    • avoid_names is a hint only. A returned name that is in the avoid set is accepted.

    The nearest-child fallback gives a centroid the exact label of one of its children, and nothing stops two centroids from getting the same name. In the next cycle the label dict in step 5 keeps only one node per label, so one of the two same-named nodes is left out of clustering and of tag matching.

    Step 9: junction (paragraph) summaries, floor-up¶

    _run_all_junction_summarisation collects every centroid whose paragraph_summary is NULL or empty and calls resolve_junction_summaries(dirty, expected_unsummarised=True). Centroids that already have a summary are not regenerated, even if new memories have since been linked to the tags under them.

    Levels: _group_by_level orders the dirty centroids so children are summarised before parents. For each dirty centroid it finds which of its child_of children are also dirty. Level 0 is the dirty centroids with no dirty children; it removes them and repeats. If no centroid is ready (a cycle in the graph), the rest go in one final level.

    Snippets: for each centroid in a level, _gather_child_snippets builds one string per child:

    • Centroid child: its paragraph_summary, or its label if it has none.
    • Leaf child: Memories tagged '<label>': s1 | s2 | s3, using up to 3 non-empty summaries of non-archived memories linked by has_tag. A leaf with no linked memories contributes its label.

    Summarise: llm.generate_junction_summaries_batch(groups) produces one summary per centroid. If it raises or returns the wrong count, the code calls llm.generate_junction_summary once per group. An empty result for one slot is also redone with generate_junction_summary. Results are written with update_junction_summaries, one transaction per level, before the next level reads them.

    LLMProvider.generate_junction_summary in the base class joins the snippets with spaces after cutting each to 120 characters. Gemini overrides it with an LLM call, so with Gemini every fallback is another model call.

    Gemini batches 8 groups per call (_JUNCTION_BATCH_CHUNK_SIZE) on up to 10 workers. generate_junction_summaries_batch.prompt asks for 2 to 4 fact-dense sentences per group that keep personal facts and proper nouns, returned as a JSON array. Snippets have \n# replaced by \n.

    Step 10: decay and archive¶

    storage.apply_decay_and_archive(decay_lambda, archive_threshold, now) runs in one transaction over memories with status='consolidated'. The current batch is still dreaming at this point, so it is not decayed in its own cycle.

    For each row:

    anchor = last_accessed if not NULL else created_at
t      = max(0, now - anchor)                 # seconds
w_new  = access_weight * exp(-decay_lambda * t)

    If w_new < archive_threshold the row becomes archived, w_new is stored, and all its has_tag edges are deleted. Otherwise w_new is stored.

    With the defaults (decay_lambda = 3e-7 per second, archive_threshold = 0.1):

    • One application halves the weight at t = ln 2 / 3e-7, about 2.31 million seconds or 26.7 days.
    • One application crosses 0.1 at t = ln 10 / 3e-7, about 7.68 million seconds or 88.8 days.

    The anchor does not move when decay is applied, and each cycle multiplies the already-decayed weight by exp(-lambda * t) again with the full elapsed time. Decay therefore compounds across cycles. For example, with cycles at day 10 and day 20 after creation and no retrieval, the stored weight after the second cycle is exp(-lambda * (10 + 20) days), not exp(-lambda * 20 days). How fast a memory is archived depends on how often dream cycles run.

    Archiving removes the memory's has_tag edges. Tag nodes and centroids stay, even if nothing links to them any more.

    Step 11: status flip¶

    The batch goes from dreaming to consolidated in one statement.

    Rollback¶

    If steps 2 to 7, 10 or 11 raise, the except block logs the error, sets the batch back to inbox, and re-raises. If that update also fails it logs "rollback itself failed". The finally block clears is_dreaming and releases the lock.

    Rollback only changes status. Each storage call commits on its own, so anything written before the failure stays: summaries, named entities, new tag nodes, centroids, child_of edges and has_tag edges. On the next cycle the same memories are processed again. Summaries are not regenerated because they are no longer empty. has_tag edges are deduplicated by the unique constraint. Clustering runs again over all nodes and writes another set of centroids.

    Example tree¶

    After one or two cycles the graph looks like this. Rectangles are centroids, rounded boxes are leaf tags, and slanted boxes are memories, linked to leaf tags by dashed has_tag edges.

    graph TD
    C3["career (centroid)"]
    C1["education (centroid)"]
    C2["work (centroid)"]
    T1("degree")
    T2("Business Administration")
    T3("Acme Corp")
    T4("junior analyst")
    T5("task management")
    M1[/"mem_a1: graduated, works at Acme Corp"/]
    M2[/"mem_b2: Todoist and Trello for tasks"/]

    C3 -->|child_of| C1
    C3 -->|child_of| C2
    C1 -->|child_of| T1
    C1 -->|child_of| T2
    C2 -->|child_of| T3
    C2 -->|child_of| T4
    M1 -.->|has_tag| T1
    M1 -.->|has_tag| T2
    M1 -.->|has_tag| T3
    M1 -.->|has_tag| T4
    M2 -.->|has_tag| T5

    task management is a noise point here: HDBSCAN put it in no cluster, so it has no parent and renders as a top-level node. mem_a1 has four tags, so it appears four times in a render that reaches all four leaves.

    Retrieval¶

    ContextHelper.build_prompt_context(task, top_k=5, depth=3)¶

    flowchart TD
    Q["Task text"] --> V{"Empty text, top_k below 1 or negative depth?"}
    V -->|yes| X["ValueError"]
    V -->|no| E["Embed task (one get_embeddings call)"]
    E --> N["get_nearest_nodes: cosine over all nodes, top_k"]
    N -->|no nodes| R0["Return empty string"]
    N --> S["get_subgraph(seed ids, depth): BFS over child_of in both directions"]
    S --> M["Add has_tag memories of reached nodes, skipping archived"]
    M --> C["_enforce_node_cap: keep seeds, drop farthest nodes above 80"]
    C --> L["resolve_centroid_names, resolve_junction_summaries (normally no-ops)"]
    L --> G{"Any nodes or memories?"}
    G -->|no| R0
    G -->|yes| T["_render_ascii_tree"]
    T --> O["Text tree for the prompt"]
    1. Embed: one embedder.get_embeddings([task]) call; row 0 is the query vector.
    2. Nearest nodes: SQLiteAdapter.get_nearest_nodes loads every node, stacks the embeddings into one matrix, computes cosine similarity with batch_cosine_similarity (zero vectors score 0), and takes the top top_k with argpartition, sorted by similarity. Leaves and centroids compete in the same ranking. This is a full scan with no index.
    3. Subgraph: get_subgraph(seed_ids, depth) does a breadth-first walk over child_of edges in both directions for depth hops. Going both ways means depth 2 from a leaf reaches its parent and its siblings. It then collects has_tag edges that point at any reached node and whose memory is not archived, and loads those memories.
    4. Node cap: _enforce_node_cap does nothing if there are 80 nodes or fewer (_NODE_CAP). Otherwise it computes breadth-first distance from the seeds over child_of edges, sorts nodes by (distance, id) with unreachable nodes last, and keeps the first max(80, number of seeds). Seeds are never dropped. Edges to dropped nodes are removed, and so are memories no longer reachable through a kept has_tag edge.
    5. Lazy resolvers: resolve_centroid_names and resolve_junction_summaries run on the kept nodes. After a completed dream cycle there are no placeholders or empty summaries, so both return without work. If they do find some (for example after step 8 or 9 failed), they log a warning and make the same LLM calls the dream cycle would, so a retrieval can trigger model calls. Neither ever raises.
    6. Render: if the subgraph has no nodes and no memories the result is an empty string. Otherwise _render_ascii_tree.

    build_prompt_context does not change access weights. Only retrieve_memories does.

    Rendering format¶

    _render_ascii_tree:

    • First line: Relevant Memory Context:.
    • Roots are nodes with no child_of parent inside the subgraph, sorted by id.
    • Each node prints as a folder line: the folder emoji (U+1F4C1), a space, and the label. Node ids are not printed.
    • A centroid with a paragraph_summary gets a para: "..." line under it. Summaries longer than 400 characters (_JUNCTION_SUMMARY_MAX_CHARS) are cut to 399 characters plus an ellipsis.
    • Under each node, child nodes come first, then the node's memories (deduplicated within that node).
    • A memory prints as the page emoji (U+1F4C4), the memory id, and the summary in quotes. Summaries longer than 300 characters (_MEMORY_SNIPPET_MAX_CHARS) are cut to 299 plus an ellipsis. raw_content is never rendered.
    • If the memory has tags or entities, a second line follows: tags: a, b · entities: X, Y. Tags are the labels of the nodes in the subgraph that the memory's has_tag edges point to.
    • Tree connectors are ├──, └── and │.
    • A node reached from a second parent prints once more as <label> (also under: <first parent label>), or (also under: top level) if it was first printed as a root, and its subtree is not repeated.
    • Memories are not deduplicated across nodes. A memory linked to three tags in the subgraph is printed three times.
    • No dates are rendered.

    Output from _render_ascii_tree on a small subgraph, with the two emoji replaced by [F] (folder) and [M] (memory):

    Relevant Memory Context:
[F] education
    para: "The user graduated with a Business Administration degree and now works at Acme Corp."

    LTP spike on retrieve_memories¶

    neuromem.tools.retrieve_memories(memory_ids, system):

    1. Loads each id with get_memory_by_id. Unknown ids are skipped without error.
    2. Collects the ids whose status is consolidated.
    3. Calls spike_access_weight(ids, now) once, which sets access_weight = 1.0 and last_accessed = now for those rows (the SQL also checks status = 'consolidated').
    4. Updates the returned dicts to show the new values.

    Memories in inbox, dreaming or archived are returned unchanged and not spiked. An archived memory stays archived and keeps no tag edges. Because the spike moves last_accessed, it also resets the decay anchor.

    Agent tools¶

    packages/neuromem-core/src/neuromem/tools.py exposes three flat functions that take the NeuroMemory instance as an argument:

    Function Arguments and defaults Behaviour
    search_memory query, top_k=5, depth=2 Calls ContextHelper.build_prompt_context with those values. No LTP.
    expand_node node_id, depth=2 Clamps depth to 5 (_EXPAND_NODE_MAX_DEPTH), calls get_subgraph([node_id], depth), applies the 80-node cap with node_id as the seed, runs both lazy resolvers and renders. Returns an empty string for an unknown id. No embedding, no LTP.
    retrieve_memories memory_ids Returns full records including raw_content and named_entities, and spikes consolidated ones.

    Google ADK wiring¶

    neuromem_adk.enable_memory(agent, db_path, *, llm=None, embedder=None, cluster_threshold=None, dream_threshold=None):

    • Creates NeuroMemory(SQLiteAdapter(db_path), llm, embedder). Missing providers default to GeminiLLMProvider and GeminiEmbeddingProvider, with the key read from GOOGLE_API_KEY or GEMINI_API_KEY (a KeyError if neither is set). cluster_threshold and dream_threshold are passed only if given.
    • Appends three tools to agent.tools: search_memory_tool(query, top_k=5, depth=2), retrieve_memories_tool(memory_ids) and expand_node_tool(node_id, depth=2). They are plain wrapper functions, so the model's tool schema does not include the system argument.
    • Adds a before_model_callback. It takes the current user message (or, failing that, the latest user event in the session), calls build_prompt_context(query) with the defaults (top_k=5, depth=3), and appends the tree after the existing system_instruction, separated by a blank line. An empty tree leaves the request unchanged.
    • Adds an after_agent_callback. It calls enqueue twice per turn: once for the user text with metadata {"role": "user", "turn": n} and once for the latest assistant text with {"role": "assistant", "turn": n}, where n is the number of session events. It does not use enqueue_session.
    • Existing callbacks are kept and run before neuromem's. A second call on the same agent raises ValueError.

    The rendered tree shows node labels but not node ids, so the model has no id from the tree to pass to expand_node_tool.

    Benchmark results¶

    See Results. On the stratified seed-42 LongMemEval_S sample scored with the official judge, the tag-graph model scores 0.746 with gemini-3-flash-preview. It is weakest on knowledge-update, temporal-reasoning and single-session-assistant questions.

    Known limitations¶

    These come from benchmarks/RESULTS.md, the Context section of ADR-005, and the code paths above.

    • Duplicates across tags: a memory is linked to every one of its tags and the renderer prints it under each tag it reaches. ADR-005 found about a third of rendered rows were duplicates, which uses prompt space without adding information.
    • No dates: enqueue_session takes no timestamp, created_at is the insert time, and the render prints no dates. Questions like "how many days ago" cannot be answered, and knowledge-update questions cannot tell an old value from a new one. Knowledge update (0.600) and temporal reasoning (0.667) are among the lowest-scoring types in the stratified run.
    • Label-vector centroids: leaf embeddings are embeddings of 1 to 4 word tag strings, and each centroid is the mean of its children's vectors. ADR-005 notes these drift towards generic centres, so a broad centroid can outrank the specific tag a question needs. RESULTS.md records the "degree" tag ranking behind centroids such as "measurement" and "qualification" at top_k=5.
    • Lossy summaries: retrieval renders only summaries, cut to 300 characters. Summaries are 2 to 4 sentences focused on the user, so details the assistant gave (a list item, a number, a chess move) are lost unless the agent calls retrieve_memories for the raw transcript. RESULTS.md also records a precision miss where two similar memories both appeared and the summaries did not distinguish them.
    • Graph growth: each cycle clusters all existing nodes again, including old centroids, and never deletes centroids, so the hierarchy gains layers and multi-parent nodes over time. Junction summaries of existing centroids are not refreshed when new memories are linked to the tags beneath them.
