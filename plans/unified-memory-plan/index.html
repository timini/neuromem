    One memory system with three linked views: final plan¶

    The base is Design 1: one schema with a view column, one leaf call, no near-duplicate merging, no ward linkage, no hdbscan, and LLMProvider reduced to complete(). Four things come from the other designs:

    • Separate jobs per view, a unified baseline on the same member sets and a links-off arm (Design 2).
    • Episodic threads anchored on labels (Designs 2 and 3).
    • The tight-budget condition, pre-registered rules, answer cache, noise floor and phase 0 metering (Design 3).
    • Turn-level evidence metrics (Design 2).

    Left out because they cost a lot of code before any evidence supports them:

    • Fact key vectors.
    • Personalized PageRank.
    • A regex temporal parser.
    • A cache inside StorageAdapter.
    • New timeline and related tools.
    • The ADK session-append rework.
    • Rented GPUs as the main path.

    Code facts checked for this plan:

    • StorageAdapter has 15 abstract methods plus set_named_entities, which is a non-abstract no-op (storage/base.py:148).
    • EpisodicMemory(db_path=...) is configurable (episodic.py:293), so episodic databases can exist on disk.
    • Nothing in neuromem-gemini reads usage_metadata or sets a thinking config.
    • Bench agents default to gemini-3.8-flash.
    • Prompt files exist in four provider packages: gemini, openai, anthropic and gemma.

    1. Conceptual model¶

    Leaves are dated memories, one per session. They are the only shared identity. Each view is a separate structure over the same leaves, and each has one job:

    View Question it answers Built from Node kinds LLM text on nodes
    Semantic (neural, the RAG tree) What is this about, and what else is like it? Leaf embedding geometry cluster TOPIC plus a topical summary. No timeline.
    Ontology (symbolic) Which memories mention X, and what kind of thing is X? Tags and entities from the leaf call label, category None. Deterministic.
    Episodic (time) What happened when, what is true now, what changed? Dates, plus ontology labels as anchors thread, week, month CURRENT and HISTORY on threads only. Periods are deterministic.
    Unified (experiment baseline) All of the above in one tree Same member sets as semantic cluster TOPIC, ENTITIES, CURRENT, HISTORY

    Views are linked in two ways:

    1. Shared leaves. A memory id is the join key. Nodes in different views are related when their member sets overlap, and this is computed at query time.
    2. One stored typed edge. A thread is anchored_to the ontology label it was built from, so "Honda Civic" the label and "Honda Civic" the timeline are explicitly the same thing.

    A memory can sit under several label nodes and several threads, so each view is a shallow DAG rather than a strict tree. The whole store is a multi-rooted DAG over one leaf set. That is the "RAG tree, but more".

    Changes to the current schema:

    • memories: add session_id, session_date, sort_key, tags, embedding and leaf_version. named_entities already exists.
    • nodes:
    • Add view, kind, member_key, member_ids, first_date, last_date, attrs and active.
    • member_key is unique together with view.
    • Rename paragraph_summary to summary.
    • Drop is_centroid, because tags are no longer nodes.
    • edges:
    • The CHECK becomes member_of (leaf to node), child_of (node to node, same view) or anchored_to (thread to label).
    • Drop weight.

    StorageAdapter contract, 12 abstract methods replacing the current 16:

    3. Dream cycle¶

    The trigger stays: a background thread at dream_threshold, or dream(block=True). The lock and the status flips are unchanged. No LLM calls run on the hot path (ADR-004).

    flowchart TD
    A["inbox: flip to dreaming"] --> B["leaf call per memory: SUMMARY, TAGS, ENTITIES"]
    B --> C["embed leaf text, chunk mean"]
    C --> D["decay and archive"]
    D --> V{"for each enabled view"}
    V --> S["semantic: average linkage, clusters of 2 to 30"]
    V --> O["ontology: labels with support 2 or more, categories by cosine cut"]
    O --> E["episodic: threads from labels, weeks and months"]
    V --> U["unified: same member sets as semantic"]
    S --> R["summarise new member_keys only, embed node text"]
    E --> R
    U --> R
    O --> R
    R --> W["replace_view per view; flip to consolidated"]

    3.1 Leaf call¶

    There is one call per memory (prompts/leaf.prompt). It reuses the MEMORY_SUMMARY_PROMPT rules: absolute dates, the original phrase in brackets, every personal fact, changed values, and assistant specifics.

    The output is a line format, not JSON, because JSON is fragile on small local models:

    SUMMARY: On 2023-05-20 (Sat), the user ...
TAGS: car purchase; honda civic; budgeting
ENTITIES: Honda Civic (product); Dave (person); Toyota dealership (organisation)
    • Tags are 3 to 8 lowercase noun phrases.
    • Entity types come from a fixed set: person, place, organisation, product, item, event, activity, other.
    • If parsing fails, the call is retried once. If it fails again, the summary becomes On <date>: <transcript head> with empty lists.
    • The fallback rate is logged, because it hurts the ontology and episodic views more than the semantic one.

    3.2 View builders¶

    Builders live in neuromem/views/ (base.py, semantic.py, ontology.py, episodic.py, unified.py). Each implements:

    • build(leaves, ctx) -> ViewGraph, which makes no storage writes.
    • rank(query, graph, leaves) -> ViewHits, which makes no LLM calls.

    All summaries go through ctx.summarise(kind, member_key, prompt), which checks get_node_cache first. A view never calls the LLM directly.

    Semantic

    • Structure: one scipy average linkage on cosine distance over leaf vectors. dendrogram_member_sets moves here from episodic.py.
    • Every internal node of 2 to 30 members becomes a cluster. child_of follows the merge order, and duplicate member sets are dropped.
    • Prompt: cluster.prompt, giving TOPIC plus a 2 to 4 sentence topical summary that keeps names and numbers but has no CURRENT or HISTORY. The input is the member summaries in date order.
    • About 40 nodes for N = 48.

    Ontology (no LLM calls)

    • Labels:
    • Normalise tags and entities: casefold, collapse whitespace, strip a leading "my" or "the", fold simple plurals.
    • Keep labels with 2 or more memories, capped at 60 by support with recency as the tie-break.
    • Labels that occur in more than N/4 memories are kept as nodes but excluded as thread anchors.
    • Label merging: embed each label as "<label> (<type>)" (short, cached by string) and merge same-type pairs at cosine 0.92 or above with union-find.
    • Categories:
    • Average linkage over the label vectors, cut at cosine distance 0.45.
    • A group of 2 or more labels becomes a category whose members are the union of its labels' members.
    • The category label is its most frequent member label, so no LLM naming is needed.
    • This replaces HDBSCAN, clustering.py and the hdbscan dependency. scipy is already a dependency.

    Episodic

    • Threads:
    • Anchors are ontology labels with at least 2 memories on at least 2 distinct dates.
    • Rank anchors by member count times date span. Drop any anchor whose member set has Jaccard above 0.8 with a higher-ranked one (entity labels win over tags). Keep at most 24.
    • One call per new member set with thread.prompt, which is the current EPISODE_PROMPT plus the line "These records all concern: ". The input is the members' dated summaries.
    • The output is CURRENT and HISTORY. Each thread gets an anchored_to edge to its label node.
    • Periods:
    • ISO week and calendar month nodes, created only with 2 or more members. A level whose node would have a single child is skipped.
    • The node text is deterministic: - <date>: <first sentence of each member summary>. No LLM.
    • Undated memories are left out of periods.

    Unified (experiment only)

    • Same member sets as semantic, so the comparison isolates how knowledge is split across nodes from how memories are clustered.
    • Prompt: unified.prompt, giving TOPIC, ENTITIES, CURRENT and HISTORY.

    3.3 LLM calls per instance¶

    These are estimates for N = 48 sessions, about 122K transcript tokens, with thinking off.

    Step Calls Input tokens Output tokens
    Leaves 48 ~145K ~22K
    Semantic clusters ~40 ~140K ~10K
    Ontology 0 0 0
    Episodic threads up to 24 ~60K ~10K
    Unified clusters (experiment only) ~40 ~145K ~18K
    Production total (no unified) ~112 ~345K ~42K
    Experiment shared build ~152 ~490K ~60K

    Embedding tokens come to about 300K per instance and are paid once through the cache. That covers leaves with and without the tag header (about 130K each), label strings (about 5K) and node text (about 30K).

    For comparison, the current EpisodicMemory makes about 48 summary calls plus 60 to 75 episode calls across two linkages, about 310K input and 36K visible output per instance.

    Incremental dreams after the first:

    • Episodic re-summarises only the threads of the new memory's labels.
    • Ontology costs nothing.
    • Semantic re-summarises the ancestors whose member set changed, as today.

    4. What is embedded¶

    Leaf text is chunked at the embedder's max_input_chars, with the header repeated on every chunk. max_input_chars is about 24,000 for gemini-embedding-2 and about 6,000 for embeddinggemma, which takes 2K tokens. Chunk vectors are normalised and averaged.

    Date: 2023-05-20 (Sat)
Tags: car purchase; honda civic; budgeting
Entities: Honda Civic (product); Dave (person); Toyota dealership (organisation)
Summary: On 2023-05-20 (Sat), the user ...

Transcript:
<chunk>

    A second "notag" leaf vector without the Tags and Entities lines is stored for the ablation in section 7. It costs only an embedding.

    Node embed text, one vector per node:

    Node Embedded text
    semantic cluster Topic: <label>\nDates: <first> to <last>\nEntities: <8 most frequent member entities>\n<summary>
    ontology label Label: <name> (<type>); category: <category>\n- <date>: <first summary sentence of each member, up to 20>
    ontology category Category: <label>\nLabels: <member labels>
    episodic thread Timeline: <anchor>\nDates: <first> to <last>\nCURRENT: ...\nHISTORY: ...
    episodic week / month Period: <range>\n- <date>: <first sentence of each member summary>
    unified cluster Topic / Entities / CURRENT / HISTORY text plus dates

    mean_embedding and the episode_embedding option are removed. Section 7 checks node scoring by node-text vector against mean-of-members vector, retrieval-only, before the removal lands.

    5. Retrieval, fusion and rendering¶

    NeuroMemory.build_context(query, *, today=None, views=None, links=True, budget="B60") makes one embedding call and no LLM calls. It returns Context(text, memory_ids, session_ids, node_ids_by_view, rankings_by_list), with everything in rank order.

    flowchart LR
    Q["query vector and text"] --> L["L: leaf cosine ranking"]
    Q --> RS["semantic.rank"]
    Q --> RO["ontology.rank"]
    Q --> RE["episodic.rank"]
    L --> F["RRF over memory lists, k=60, weight 1"]
    RS --> F
    RO --> F
    RE --> F
    RS --> NS["node pool: per-view quota, Jaccard 0.8 dedupe"]
    RO --> NS
    RE --> NS
    F --> LK["link following: overlap and anchored_to"]
    LK --> NS
    F --> R["render under fixed budget"]
    NS --> R

    Memory lists:

    • L (always on): leaf cosine.
    • Semantic: memories ordered by the rank of the best-ranked cluster that contains them, with ties broken by leaf cosine.
    • Ontology:
    • Exact match of casefolded query n-grams against label strings comes first, then labels by cosine.
    • Memories are ordered by their best label rank.
    • Exact names are the main thing the symbolic view adds.
    • Episodic:
    • Threads are ranked by cosine. Members of the top threads come first, latest first.
    • Week and month nodes are ranked by cosine like any other node. No date parser is used.
    • Fusion: score(m) = sum over lists of 1 / (60 + rank).
    • A single-view arm is L plus that view, which measures what the view adds on top of leaves.
    • Transcripts go to the top 3 fused memories.

    Node selection:

    • Each active view puts its top 10 nodes into the pool. They are interleaved by per-view rank.
    • Each view gets an equal share of the node budget. The unified arm gets the whole budget.
    • A node is skipped if its member set overlaps an already chosen node, in any view, by more than 0.8 Jaccard.

    Link following is on in M and off in M-nolink:

    • A node in another active view that contains at least 2 of the top 5 fused memories joins the pool.
    • A chosen thread pulls in its anchored_to label.

    Fixed budgets, identical across arms:

    Condition Total Nodes Memory lines Transcripts
    B60 60K chars up to 15K rest 3, capped at 12K each
    B12 12K chars up to 5K rest none

    The arm without nodes (F) spends the node budget on extra memory lines.

    Render format, with each memory appearing once and a section shown only if its view is active:

    Today's date: 2023-05-30 (Tue)

## Timelines
### honda civic (3 memories, 2023-05-20 to 2023-06-02) [t_ab12]
CURRENT: ...
HISTORY: ...
## Topics
### car purchase and insurance (2023-05-20 to 2023-05-27) [c_cd34]
...
## Labels
honda civic (product) > vehicles: mem_ab12 2023-05-20, mem_ef56 2023-06-02

## Memories (oldest first)
[2023-05-20 (Sat)] mem_ab12: On 2023-05-20 (Sat), the user ...
  tags: car purchase; honda civic | entities: Honda Civic; Dave

## Transcripts
### mem_ab12 (2023-05-20 (Sat))
user: ...

    This removes the tag graph's duplicate rows and its undated output.

    6. What carries over and what is deleted¶

    Carries over¶

    • StorageAdapter pattern and SQLiteAdapter. The contract shrinks to the 12 methods in section 2.
    • Decay and archive on leaves.
    • Wall-clock based, as today. Session dates are content, not access times.
    • Archived leaves drop out of every view at the next dream, and a node whose members are all archived goes inactive. Nodes do not decay.
    • The benchmark sets decay_lambda=0.
    • LTP. retrieve_memories(ids) spikes access_weight. build_context and expand_node do not spike (ADR-003 D4). access_weight is not used in ranking during the experiment.
    • Tools. There are still three:
    • search_memory(query, system) returns build_context(query).text. The depth argument goes.
    • expand_node(node_id, system) works in any view. It returns the summary, child_of children, member rows, and an "Also in" line: the anchored_to partner plus the top nodes in other views by member Jaccard. This is where the cross-view links are visible to an agent.
    • retrieve_memories is unchanged.
    • ADK.
    • callbacks.py and memory_service.py replace ContextHelper(memory).build_prompt_context(query) with memory.build_context(query).text.
    • memory_service.search_memory builds MemoryEntry objects from Context.memory_ids instead of parsing ids out of the rendered text.
    • enable.py keeps the NeuroMemory name, drops cluster_threshold and adds views=.
    • Per-turn capture stays as it is.
    • Providers. LLMProvider shrinks to:
    • complete(prompt, *, purpose="", max_output_tokens=None) -> str;
    • a last_usage attribute holding input, output and thinking tokens;
    • a thinking-level setting.

    GeminiLLMProvider reads usage_metadata and sets the lowest thinking level for dream calls. Provider packages become transport plus rate limiting. Prompts move into neuromem-core/src/neuromem/prompts/ as leaf, cluster, thread and unified.

    Migration and ADR¶

    • Version 0.2.0, a breaking change. Third-party adapters and providers break. The changelog lists old and new methods.
    • neuromem.storage.sqlite.migrate_v2(db_path):
    • Adds the schema_version table and the new memories columns.
    • Drops and recreates nodes and edges.
    • Sets consolidated memories back to inbox with leaf_version = NULL, so the next dream rebuilds everything from raw_content. That costs one leaf call per memory plus the view builds.
    • SQLiteAdapter.__init__ raises StorageError naming migrate_v2 when it finds the old schema, rather than migrating silently.
    • scripts/migrate_episodic.py imports ep_memories rows (raw_content, session_id, session_date) from on-disk EpisodicMemory databases into the new schema as inbox.
    • ADR-006, "One memory model: dated leaves and linked views":
    • Supersedes ADR-001, ADR-002, ADR-003 D1 and D2, and ADR-005.
    • Keeps ADR-003 D4 and ADR-004.
    • Records the leaf prompt, the embed text, the views and their jobs, links, fusion, the removal of hdbscan and the reduction of LLMProvider.
    • The default views stays open (status Proposed) until the experiment reports. The rule from section 7.6 that fired is then recorded.

    7. The experiment¶

    7.1 Cost: what can and cannot be said¶

    • Actual spend cannot be read from the repo. No provider records usage, so check the Google billing console for the real figure. Phase 0 makes spend measurable from here on.
    • The model did not get cheaper. The uncommitted diff moves bench defaults from gemini-2.0-flash-001, which is retired, to gemini-3.8-flash, a newer and more expensive tier. The spending cap was most likely reached by:
    • running two agents on 60-instance samples, plus reruns, at about 310K input tokens per instance each;
    • thinking tokens, which are not configured, so Gemini 3.x flash models think by default and bill thinking as output.

    The second point is unverified until phase 0. - Cost is computed from a CLI price table (--price model=in_per_M,out_per_M): cost = input x p_in + (output + thinking) x p_out. No price is hard-coded, and none is asserted here. - Cheaper levers, in order: 1. Thinking off for dream calls. 2. A local dream model (7.4). 3. The Batch API for dream calls, at half the price of standard calls. 4. A lite model for dream calls.

    7.2 Phase 0: measure first (one instance)¶

    • Add last_usage to every provider, with input, output and thinking tokens. Gemini reads them from usage_metadata.
    • Add the thinking-level setting and the bench cache (7.5).
    • Run one instance of the current episodic agent to get the real tokens per phase (leaf, node, answer, judge) and the thinking share.
    • Time one instance of the leaf and thread calls on the local model.

    7.3 Arms¶

    Every arm shares the leaves, the leaf vectors, the L ranking, the answer model and prompt (episodic_answer.prompt), the judge, the budget conditions, the transcript count and the fusion constant. Arms differ only in which views feed fusion, node selection and rendering.

    Arm Views on top of leaves Purpose Tier R Tier A
    F none Does any structure help? Yes Yes
    F-notag none, old leaf text without tags and entities Tags-in-embedding ablation; anchor to the old 40-of-43 top-3 leaf ranks Yes No
    U unified Single merged tree Yes Yes
    S, O, E one view each Which view carries a gain Yes Best one only
    SO, SE, OE pairs Interactions Yes No
    M semantic + ontology + episodic, links on The neuro-symbolic proposal Yes Yes
    M-nolink as M, link following off Do cross-view links matter? Yes No

    F-notag needs no tree, so it is a free anchor. The old 40-of-43 figure is a leaf-ranking result, and F-notag reproduces that setup with the new code.

    Conditions:

    • B60 is close to today's 63K median context.
    • B12 has no transcripts and is the condition that can separate arms. At B60 every arm is likely to be at ceiling.

    7.4 Where the LLM work runs¶

    Work Where Notes
    Leaf and node calls (dream) Ollama locally, qwen3:8b or gemma3:12b Primary path, $0
    Embeddings gemini-embedding-2, cached Keeps leaf vectors comparable to earlier runs; paid once
    Answer and judge gemini-3.8-flash, temperature 0, cached Keeps the official judge fixed

    Local setup:

    • build_pair("gemma", model=...) already reaches any Ollama model through the OpenAI-compatible endpoint. The merged agent must use it.
    • Set OLLAMA_CONTEXT_LENGTH=16384, or num_ctx in a Modelfile. The OpenAI-compatible endpoint takes no per-request num_ctx, and Ollama's default silently truncates sessions. The longest sessions are about 11K tokens.
    • Turn Qwen3 thinking off.
    • If embeddinggemma is ever used, chunks must drop to about 6,000 characters, and all arms must share it.
    • The machine is an M4 with 16 GB. gemma3:12b is tight at a 16K context, and qwen3:8b is the safer default.

    Throughput is not extrapolated:

    • Time one instance, then compute hours = instances x (490K / prefill tok/s + 60K / decode tok/s) / 3600.
    • At an assumed 300 tok/s prefill and 20 tok/s decode, that is about 1.3 hours per instance, or about 75 hours for 60.
    • If the timed figure is that slow, there are four options:
    • run the 60 instances across several nights;
    • use qwen3:4b;
    • build the dream on Gemini with thinking off through the Batch API;
    • run Tier R on fewer instances first.
    • A local dream changes absolute accuracy, so arms are compared within the run only. F-notag and U are the in-run anchors.

    7.5 Caching (neuromem_bench/_cache.py, file ~/.cache/neuromem-bench/cache.sqlite)¶

    • CachedLLM(inner): table llm(key PK, text, input_tokens, output_tokens, thinking_tokens, latency), keyed on sha256(provider, model, purpose, prompt).
    • CachedEmbedder(inner): table emb(key PK, vector), keyed on sha256(model, dim, text).
    • Answer cache: keyed on sha256(model, prompt_version, context_text, question). Two arms that render the same context get the same answer, so a discordant pair cannot come from sampling noise alone.
    • Phase 1: for each instance, build the leaves and all four view sets (semantic, ontology, episodic, unified) once into artifacts/<instance_id>.db. The views coexist, separated by view.
    • Phase 2: loop over the arms on that database with build_context(..., views=..., links=...). Arms never trigger a build call.

    Within the 60-instance sample only about 4% of sessions repeat across instances. The cache therefore pays off across arms and reruns, not across instances.

    Cache rows record tokens. The runner can therefore report each arm's "built alone" cost without paying for it twice.

    7.6 Tiers, metrics, statistics and decision rules¶

    Sample: LongMemEval_S, stratified 10 per type, seed 42 (60 questions), the same set as earlier runs. It extends to 20 per type (120) for Tier R if 7.7 allows.

    Tier R (retrieval only, primary, no answer LLM). It runs for all arms under both conditions. Metrics per question and arm:

    • Rank of the first answer session in the fused list, and its reciprocal rank.
    • recall@3 (the transcript slots), and all-evidence@3 for multi-session questions. recall@12 is already at ceiling (43 of 43), so it is reported but not used.
    • Session recall at B12: the share of answer sessions whose memory line or node membership reached the context.
    • Evidence-turn coverage: the share of has_answer turns whose session transcript, or whose memory line, is in the context, reported separately. The count of labelled turns is taken from the data at run time.
    • Context characters per section and nodes per view.
    • View distinctness for M: the mean over nodes of the best Jaccard with any node in another view.
    • Two node-vector checks:
    • leaf ranking with the notag vectors against the tagged ones;
    • node scoring by node-text vector against mean-of-members vector.
    • Statistics:
    • Paired Wilcoxon signed-rank on reciprocal rank and on B12 session recall.
    • Bootstrap 95% CI of the mean paired difference, with 10,000 resamples over questions.
    • Holm correction across the pre-registered comparisons: M vs U, U vs F, M vs F and M vs M-nolink.
    • Per-type results are descriptive only.

    Tier A (answers and the official judge). Arms F, U, M, plus the best single view if Tier R names one, at both budgets, n = 60.

    • Accuracy overall and per type, with Wilson 95% intervals. Abstention questions are reported separately.
    • Exact McNemar on discordant pairs. At accuracy near 0.9, p < 0.05 needs about a 6 to 0 or 8 to 1 split, so 7 to 1 is not enough. Accuracy is therefore a non-inferiority guard: an arm is non-inferior when its losses exceed its wins by at most 2 at both budgets.
    • Noise floor: U at B60 is answered a second time with the answer cache off, and the flip rate is recorded. A discordance count at or below that rate is noise.

    Cost and time metrics. For every arm: input, output and thinking tokens per phase (leaf, each view, answer, judge), both paid and built-alone equivalent. Also dream wall time per view, retrieval latency, and cost from the price table.

    Decision rules (fixed before running; no constant is tuned on the 60).

    1. Flat wins if neither U nor M beats F on B12 session recall by at least 0.05 with a CI excluding 0, and F is non-inferior on accuracy. Ship leaves only for retrieval, and keep the cheapest view only if expand_node needs it.
    2. Unified wins if U beats F under rule 1 and M does not beat U by at least 0.05 with a CI excluding 0.
    3. Linked views win if all of the following hold:
    4. M beats U by at least 0.05 on B12 recall with a CI excluding 0;
    5. M is non-inferior on accuracy;
    6. M's measured dream tokens are at most 1.3 times U's;
    7. M's view distinctness is below 0.5.
    8. Links matter if M beats M-nolink on reciprocal rank (Wilcoxon, Holm-corrected). If they do not, drop link following but keep the stored anchored_to edge for expand_node.
    9. One view is enough if a single view or pair recovers at least 80% of M's gain over F. Ship leaves plus that view.
    10. Tags stay in the leaf text if F is non-inferior to F-notag on reciprocal rank (one-sided, margin 0.02). Whatever the result, tags and entities stay in the render.

    Known limits:

    • The median LongMemEval_S history spans about 10 days, so periods barely exist. The episodic view is tested mostly through threads, and conclusions about long timelines need a longer-span dataset.
    • With 10 questions per type, per-type patterns must not pick the architecture.
